## 2026-07-22 — QQNT 私聊方向字段误判

- 阶段：身份归一化与历史修复
- 类型：API契约 / 功能行为
- 现象：私聊消息的发送者身份和左右视角反转。
- 根因：不能仅凭字段名称猜测 QQNT `40020/40021` 的方向语义；真实样本表明 `40020 != 40021` 才表示当前账号发送，`40020 == 40021` 表示对方发送。
- 修复或规避：解析器、查询层和历史修复脚本统一使用真实字段组合判断方向；按 `40030` 归一化私聊对方 QQ 号。
- 预防规则：协议字段语义必须用真实收发样本交叉验证，并同时检查发送者 QQ、昵称、原始 UID 和 UI 左右位置。
- 验证证据：生产私聊查询验证自己 `1248465005` 为 `out=true`，对方 `274614336` 为 `out=false`；容器版本 `perspective-fix-20260723` 健康检查通过。

- 阶段：消息去重与历史数据修复

## 2026-07-27 — 回复预览跨账号泄露会话内容

- 阶段：W2 安全与一致性（FQ-15）
- 类型：安全 / API契约 / 一致性
- 现象：消息列表和搜索结果里的回复预览，可能显示成另一个账号、另一个房间那条消息的发送者昵称与正文，调用方对该会话本来没有任何可见权限。

- 附带自查：待解析集合一度按裸 ID 求差，会让"该 ID 已在 A 房间命中"直接跳过 B 房间的别名回查而静默丢预览，跨房间搜索页真会触发；已改为全程按 `(房间, 回复 ID)` 二元组求差与回填，并补了对应回归。

## 2026-07-27 — 照灾备文档配置会让自动备份永久静默停摆

- 阶段：W2 安全与一致性（FQ-27）
- 类型：部署 / 可观测性 / 文档
- 现象：按 `DISASTER_RECOVERY.md` 的建议提高备份频率后，自动备份再也没有执行过，但 Web 控制台的备份状态一直显示“开启”，只有 `data/backups/failures.log` 在以每分钟一条的速度无限增长。
- 根因：调度器只接受 `分 时 * * *` 的纯数字 cron，而灾备文档却让运维提高频率，写 `0 */6 * * *` 必然抛错。该错误被循环最外层的 `except Exception` 通吃，于是变成“记日志 + 追加失败记录 + sleep 60”的永久循环。三层后果叠加：备份不再执行、失败日志无上限增长、状态接口仍报 `enabled: true`——配置错误没有任何一条对外可见的信号。
- 修复或规避：分钟与小时字段扩展为支持 `*`、数字、范围、步长与逗号列表（日/月/星期仍限定 `*`，即“每天重复”）；对各实现语义不一致的 `5/10` 明确报错而不是猜。cron 解析失败从外层通吃里拆出来，按值去重、只在值变化时报一次，并继续轮询以便改回正确值后自动恢复。状态接口增加 `cron_error` 与 `next_run_at`，前端在计划无法执行时显示“开启（计划无法执行）”加具体错误。文档写明受支持的子集与反例。
- 预防规则：文档里出现的每一种配置写法，都必须有测试证明实现真的接受它——文档与实现的差距要用测试锁住，不能靠人读。配置类错误不能和运行时错误共用一个 catch：前者不会自愈，重试没有意义，必须去重上报并暴露到状态接口，否则就是静默停摆。任何“开关已打开”的字段都不等于“功能真的在跑”，状态接口要能区分这两者。
- 验证证据：新增 4 组回归——文档里的各种子日频率均可解析、`0 */6` 跨午夜正确进位、9 种无法调度的表达式一律抛错、调度循环跑 5 轮后 `failures.log` 只有 1 条记录（修复前每轮 1 条）；另有 API 层 `cron_error` 断言与前端契约断言。

- Symptom: Production PostgreSQL backup passed about 62,000 message hashes to one `robot_messages.msg_hash IN (...)` query. asyncpg rejected it because a query cannot exceed 32,767 arguments.
- Root cause: `BackupService.export_package()` used one full `msg_hashes` list for robot associations, import source records, and media references. Small SQLite fixtures never reached the driver parameter limit.
- Fix or workaround: Split those relation queries into batches of 1,000 hashes, then merge them by the original sort keys. Do not switch the deployment until a new signed backup succeeds.
- Prevention rule: Any data-derived `IN` collection for an external database driver must be batched. Tests must force multiple batches with a reduced threshold instead of relying on small exports.
