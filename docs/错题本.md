# 错题本

## 2026-07-22 — QQNT 私聊方向字段误判

- 阶段：身份归一化与历史修复
- 类型：API契约 / 功能行为
- 现象：私聊消息的发送者身份和左右视角反转。
- 根因：不能仅凭字段名称猜测 QQNT `40020/40021` 的方向语义；真实样本表明 `40020 != 40021` 才表示当前账号发送，`40020 == 40021` 表示对方发送。
- 修复或规避：解析器、查询层和历史修复脚本统一使用真实字段组合判断方向；按 `40030` 归一化私聊对方 QQ 号。
- 预防规则：协议字段语义必须用真实收发样本交叉验证，并同时检查发送者 QQ、昵称、原始 UID 和 UI 左右位置。
- 验证证据：生产私聊查询验证自己 `1248465005` 为 `out=true`，对方 `274614336` 为 `out=false`；容器版本 `perspective-fix-20260723` 健康检查通过。

## 2026-07-22 — 重复消息跨来源收敛

- 阶段：消息去重与历史数据修复
- 类型：编码 / 功能行为
- 现象：同一内容因 QQNT 原始事件 ID 不同生成多条消息。
- 根因：旧逻辑只按原始事件 ID 和消息哈希去重，不能识别同会话、同发送者、同时间、同内容的跨来源记录。
- 修复或规避：新增受约束的语义去重；历史修复脚本先迁移来源、媒体和分段引用，再合并消息实体。
- 预防规则：协议事件 ID 只作为来源标识，统一归档必须保留语义去重层；合并前必须处理外键和唯一约束。
- 验证证据：历史合并 `1460` 条重复行；修复后私聊语义重复组为 `0`；数据库备份在应用修复前生成。

## 2026-07-22 — 阶段复盘

- 阶段：部署收尾
- 类型：部署
- 现象：首次重建容器时网络别名参数冲突，容器未启动。
- 根因：同一容器连接多个 Docker 网络时重复指定别名。
- 修复或规避：先连接主网络，再单独连接第二网络并指定别名；保留数据卷不变。
- 预防规则：重建容器前记录原有挂载、端口和网络，网络别名只在目标网络上声明一次。
- 验证证据：最终容器 `/health` 返回正常，数据库、存储和备份检查均通过；工作树提交前复核。
## 2026-07-22 — 发布前审计：安全依赖与测试门禁

- 阶段：发布前最终审计
- 类型：安全 / 测试 / 性能 / 环境
- 现象：完整测试通过，但测试耗时超过八分钟；依赖扫描发现 Starlette 已知漏洞；Docker CLI 无 Compose 插件导致本地 Compose 无法解析。
- 根因：发布门禁此前只验证功能正确性，没有把依赖漏洞、历史导入吞吐、Compose 工具链和安全边界作为同等门禁；Collector 队列逐条开启 SQLite 事务，前端实时刷新还会周期性扫描房间来源记录。
- 修复或规避：本阶段未修改业务代码；已将问题、证据、优先级和发布队列固化到 `docs/release-final-audit-2026-07-22.md`，并明确升级依赖、批量事务、鉴权媒体和流式请求限制为发布前任务。
- 预防规则：发布前必须同时执行功能测试、依赖漏洞扫描、容器配置校验、核心链路基准和鉴权边界测试；测试全绿不等于可发布。
- 验证证据：`280 passed in 506.87s`；编译和静态资源校验通过；`pip check` 通过；`pip-audit` 报告 Starlette 0.47.3 的 8 条漏洞记录；Docker Compose 解析因本机缺少 Compose 插件未完成。

## 2026-07-22 — 发布加固：媒体鉴权与依赖升级

- 阶段：发布前最终审计修复
- 类型：安全 / API契约 / 测试 / 前端
- 现象：媒体目录可被静态路由直接读取；浏览器持久化管理令牌；同秒消息翻页会漏记录；旧测试环境遗漏 Collector GUI 依赖；初始依赖升级后仍被新增 Starlette 漏洞命中。
- 根因：媒体路径、鉴权会话和历史静态前缀耦合；时间戳不是充分游标；根测试依赖没有覆盖 Collector GUI；只按旧漏洞报告选择依赖版本。
- 修复或规避：媒体改由鉴权路由提供并迁移浏览器到 HttpOnly Cookie；下载链路校验 URL 与私网地址并限制体积；消息使用时间戳、源序号和哈希复合游标；保留 `/static/storage/` 兼容读取；根测试依赖补齐 `Pillow` 与 `pystray`；FastAPI/Starlette 固定为 `0.139.2/1.3.1`。
- 预防规则：涉及存储前缀调整时，必须同时验证新路径、旧数据兼容和鉴权；发布前以当日 `pip-audit` 结果而非历史固定版本为准；测试依赖应覆盖所有被收集模块。
- 验证证据：`285 passed`；`python scripts/minify_static_assets.py --check` 通过；`python -m pip_audit -r requirements-prod.txt` 报告 `No known vulnerabilities found`。

## 2026-07-23 — NapCat/QQNT 媒体状态与 CQ 表情混淆

- 阶段：线上媒体导入问题复核
- 类型：API契约 / 功能行为 / 部署
- 现象：界面将大量图片、GIF、视频显示为“未下载”，部分表情显示 CQ 原始参数或 `[object Object]`。
- 根因：当前 `import_sources` 仅有 `qqnt_local_db`，其 `not_downloaded` 表示源 QQNT 设备本地没有原始文件，并非 NapCat HTTP 下载失败；实时 OneBot/NapCat 下载另有 `media_assets` 并发去重竞争，重复 MD5 插入会中断 WebSocket 消费；CQ 渲染没有将 `face.raw` 的 JSON / `[object Object]` 规范化为表情名称，且视频白名单未涵盖常见通用响应 MIME 和 T264/T265 兼容策略。
- 修复或规避：后续修复应分别标识 QQNT 历史媒体与 NapCat 实时媒体；媒体资产保存使用数据库冲突安全的 upsert/retry；从结构化 `message` 段恢复表情元数据并提供 face/mface 渲染；对可信 QQ 多媒体域名加入受限 MIME 嗅探与转码回退。
- 预防规则：媒体状态必须保留来源和失败原因；不得把“源端未下载”当作“NAS 下载失败”；任何网络媒体去重都必须能承受并发相同内容写入。
- 验证证据：2026-07-23 线上库中 `qqnt_local_db` 源为 2 个；媒体引用中 image `not_downloaded/metadata_only` 为 20510、video 为 381；CQ 类型含 face 754、video 541；容器日志记录了 `media_assets_pkey` 重复键导致的 OneBot WebSocket 异常。

## 2026-07-23 — NapCat 媒体归档与 CQ 表情修复完成

- 阶段：发布前最终审计修复
- 类型：功能行为 / API契约 / 测试 / 部署
- 现象：相同媒体并发归档可能因唯一键冲突断开 OneBot WebSocket；QQNT 源端未下载媒体被误称为 NAS 下载失败；NapCat 表情与通用 MIME 视频无法稳定呈现或归档。
- 根因：`media_assets` 使用“先查询后插入”且内部提交事务；WebSocket 未隔离单条消息异常；前端和结构化分段未归一化 face 原始对象；QQ 可信多媒体视频响应可能以通用 MIME 返回。
- 修复或规避：媒体资产改为原子文件落盘和 SQLite/PostgreSQL 冲突安全 upsert，并由外层消息事务提交；WebSocket 对每条消息回滚、记录指标并继续处理；结构化 `face/mface/market_face/bface` 归一化、下载和渲染；仅对可信 QQ 域的 `application/octet-stream` 视频在 MP4/EBML 签名验证后接收；API 推导 `availability_reason`，前端区分 QQNT 源端未下载与 NapCat 归档失败。
- 预防规则：媒体写入不得在辅助函数内抢占事务边界；实时协议消费必须按事件隔离失败；不可播放或未归档的媒体必须保留来源原因，不能以原 CQ 或对象字符串代替可读提示；通用 MIME 放行必须同时限制来源域和文件签名。
- 验证证据：新增表情、动画表情、可信 QQ 通用 MIME 视频和 WebSocket 单事件失败回归；定向测试 `61 passed`；全量门禁 `291 passed`，压缩产物、Python 与 JavaScript 语法检查通过，`pip-audit` 报告 `No known vulnerabilities found`。

## 2026-07-23 — 自账号历史聊天缺失

- 阶段：WebUI 账号视图修复
- 类型：功能行为 / API契约 / 测试
- 现象：点击自己的 QQ 账号后，WebUI 只显示少量聊天；历史 QQNT 导入的其他会话未出现在会话列表。
- 根因：`QueryService` 仅通过 `RobotMessage` 判断账号可见范围；部分历史导入记录已经通过 `MessageSourceRecord -> ImportSource.account_id` 归属账号，但没有建立 `RobotMessage` 关联。
- 修复或规避：账号视图查询统一使用 `RobotMessage` 或匹配账号、平台的导入源记录；对 `rooms`、`messages`、搜索和定位查询保持同一范围规则，并使用显式别名避免 SQL 自动关联歧义。
- 预防规则：历史导入和实时采集必须共享账号视图范围；修复关联数据前，查询层不能把缺失的派生关联当作数据不存在；账号范围回退必须同时限定账号和平台。
- 验证证据：新增“仅有导入源记录、无 RobotMessage”回归；定向查询/导入测试 `44 passed`；全量测试 `291 passed`，另有 1 条既有 Collector 环境断言不匹配，未涉及本次代码。

## 2026-07-23 — 头像补全异常击穿会话列表

- 阶段：WebUI 账号视图修复
- 类型：功能行为 / API契约
- 现象：点击账号后仅显示旧的少量会话；`/api/rooms` 返回 500，前端保留上一次成功加载的列表。
- 根因：房间列表接口在返回数据前同步补全 QQ 头像；单个头像资产写入异常未隔离，导致整个列表请求失败。
- 修复或规避：按会话捕获群/好友头像补全异常并回滚当前事务；头像服务本身降级为无头像但继续保存会话资料。
- 预防规则：任何列表查询中的资料补全、网络请求或媒体写入都不得成为主查询的单点失败；必须有逐项隔离和回归测试。
- 验证证据：新增 `test_rooms_api_keeps_all_rooms_when_avatar_hydration_fails`；线上日志已确认失败栈位于 `list_rooms -> _hydrate_missing_room_profiles -> save_media_asset`。
