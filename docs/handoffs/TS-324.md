## 变更与复用

历史 key 已可能泄露，必须既证明历史内容与受信工件完全匹配，又验证该工件的旧 HMAC。
仅知道旧 key、伪造包内 key_id/时间、改变文件路径或重算 checksum 不能建立历史信任。

`app/backup/trust.py` 拥有显式 `BackupVerificationPolicy`、有界 registry 加载和内容指纹；
复用既有 canonical JSON 规则（实现归入该领域模块，archive 继续导入同一函数）、
legacy 的实际 canonical replay、v4 的实际 member framing。指纹为：

```text
SHA256(canonical_json({
  domain: "chat-audit-core.backup-content.v1",
  format: "legacy-json" | "v4",
  payload_sha256: <实际重算摘要>,
  manifest: <完整解析后的manifest，包含checksum/signature及其metadata>
}))
```

HTTP `BackupService.validate_import_package`、流式 legacy integrity 和 v4 manifest 验证三个原核心
都显式接收 policy。核心调用方、HTTP preview/import、CLI validate/fingerprint/convert/restore
及 package-level v4 别名复用原验证函数，不隐藏读取 Settings 或提供全局旧 key fallback。

legacy 输入只解析一次形成既有稳定 spools；旧 key 只在实际内容 pin 命中后用于该快照重放。
v4 单次流式重算 payload SHA 与各少量历史 HMAC，manifest 最后到达时必须精确 pin 命中且
同一个 key 的 payload/manifest 双 HMAC 都正确才可接受。没有巨大 raw 备份额外复制或
先 hash 路径再重开输入的信任判断。

输出 writer/exporter/worker 仍只获得当前 `APP_SECRET_KEY`。转换历史输入的 policy 与当前输出
signing_key 分开传递，转换结果只由当前 key 签发。cursor 未接 policy，沿原独立域派生当前 key。

保留 `BACKUP_IMPORT_REQUIRE_SIGNATURE=false`、unsigned 管理员导入及 `signature_valid=null`；
原媒体完整性、转换临时文件清理、v4 隔离恢复的空目标规则沿用原实现。

## 配置和管理员操作

`BACKUP_TRUST_REGISTRY` 默认为空，值为外置 JSON 文件路径。`.env.example` 与 Compose app/
backup-worker 两服务传递该可选设置；挂载/真实私密文件由父协调者部署管理，产品不自建信任目录。

```json
{
  "schema": "chat-audit-core.backup-trust.v1",
  "historical_keys": {"previous": "EXAMPLE-ONLY-OLD-KEY"},
  "trusted_backups": {"<64 lowercase hex content fingerprint>": "previous"}
}
```

文件上限 2 MiB、历史 key 上限 16。文件错误、缺失、重复 JSON key、错误 schema 或悬空引用
只关闭历史验证，当前验证仍可使用；日志只说明异常类型，不打印 secret、文件内容或异常文本。

切换前，在原 key 为当前 key 的受控环境，从管理员已核来源的材料执行：

```bash
python -m app.backup.cli fingerprint /trusted/old.json.gz --format legacy
python -m app.backup.cli fingerprint /trusted/old.cacb --format v4
```

命令要求 checksum 与签名通过，只输出内容指纹，不写 registry，不把候选请求自登记。
旧 key 知情人也能产生有效签名，所以“签名通过”不能替代父协调者对历史工件来源的核验。
部署与恢复操作说明位于 `DISASTER_RECOVERY.md` 的签名轮换段。

## 独立候选审查返修

父协调者的一次独立 candidate review 复现了合法回归：JSON 可表示的 lone surrogate
历史 key 能进入 policy，v4 accumulator 在检验当前签名前编码全部历史 key 时抛出
`UnicodeEncodeError`。本检出已先重现该异常，再在 `BackupVerificationPolicy` 构造边界统一
校验历史 key 可按 UTF-8 编码；失败以不含 key 的固定 `ValueError` 拒绝，loader 沿原分支
关闭该清单的历史信任，保持当前 key 工作。没有改其他冻结实现或生产保留策略。

新增 2 个精确用例：直接构造拒绝及错误文本不泄 key；坏 surrogate registry 清空历史信任、
诊断脱敏，并保当前 key 的 legacy/v4 实际验证通过。本地构造 pytest **1 passed / 22 deselected**；
Windows 直接脚本通过真实 loader、legacy validator 与 v4 public validator 同时证明坏 registry
不阻断当前签名，无平台 shim。变动的 2 个 Python 文件语法及 diff-check 通过。

## 上线恢复必需的启动迁移修复

父协调者随后以生产 PG 元数据证实：新 app 在监听前的 `ensure_schema_compatibility` 中
等待 `DROP INDEX`，被仍在运行的 worker 只读备份事务阻挡。此初始化行为在基线即已存在：
每次启动无条件重跑迁移 012 创建两个 index、再由 015 删除。父协调者明确授权本修复，
代码范围补充 `app/database.py` 与相关迁移/启动测试；本检出未操作生产或备份保留策略。

`ensure_schema_compatibility` 现在在原同一事务中读取既有 `schema_migrations` 版本集合，
只 apply 并 record 尚未完成的版本。首次初始化、无 journal 的旧库仍正常执行全部迁移；
已有 rollback 会删除对应版本 marker，因此下次启动正常重放该迁移。原模型表初始化保留。
没有现有测试或调用契约要求每次重跑一次性媒体合并/DDL，故不引入额外 repair 路径。
